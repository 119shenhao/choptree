# ChopTree · AI 开发与记忆工作流程

前置：[START_HERE.md](./START_HERE.md) → [PROJECT_STATUS.md](./PROJECT_STATUS.md)。
本文件负责「任务分流、信息分类、文档更新、验证和交接」。

## 固定主流程

**读取入口 → 核对项目状态 → 判断任务类型 → 按需读取文档/代码 → 讨论或执行 → 主动捕获重要信息 → 验证 → 写入并核验 GitHub → 更新交接状态。**

不要只凭上一次聊天的记忆执行写入操作。读取最新文件，必要时核对最新提交及网站部署来源。

## 主动判断是否要记录（默认由 AI 负责）

**A. 明确且影响未来：立即正式记录。**
包括用户明确确认的需求、重要限制、优先级、验收标准、确定的技术方案、重大发现以及执行结果。放入对应正式文档，更新状态；不必让用户再次说「记下来」。

**B. 可能重要但尚未确定：先保全，再确认。**
包括「以后可能」「我考虑」「要不要」「也许」等持久性想法，或 AI 无法判断是否为定案的规则。可先在 [IDEAS_INBOX.md](./IDEAS_INBOX.md) 记录为**候选 / 待确认**，不作为开发授权或正式需求；在合适的时机简短询问用户是否确定，或请用户纠正候选内容。用户确认后移入正式文档、保留引用；否定后标记已否决，不反复询问。

**C. 临时、重复、无关：一般不记录。**
问候、语音断连、无长期意义的闲聊、重复内容不产生新记录。敏感内容和凭据不得未经明确授权写入仓库；若用户要求不记录，遵从其意愿。

**判断不清时：** 只问一个真正影响决定的核心问题，不强迫用户记住分类规则。若本轮未能得到确认，候选可保留为待确认；**绝不能当作正式需求直接开发**。

## 何时保存

- 不等待聊天结束：**在已确认重要决定、明确阶段结论或开发里程碑出现时**就更新 GitHub；长任务在有价值的可恢复节点留下进度。
- 如果讨论还没有阶段性结论，可把值得保全的想法暂存候选，不必为每句话提交一次。
- 每次保存应先核对现有内容，更新关联文档；不要靠纯聊天记忆认定已保存。
- 若 GitHub 不可用，直接告知本轮内容**未持久化**，在对话中给出可供之后补录的准确文本；不要假装排队后台自动提交。

## GitHub 提交与验收

1. 确认目标仓库 / 分支和当前文档版本，避免覆盖别人的修改。
2. 修改代码和相应文档；按任务需要执行测试或明确说明未测试。
3. 提交后重新读取相关文件或核验提交 / 分支状态，记下 Commit SHA。
4. 更新 [PROJECT_STATUS.md](./PROJECT_STATUS.md) 和必要的 [WORK_LOG.md](./WORK_LOG.md)，说明已完成、未完成、阻塞、后续动作。
5. 向用户简洁报告：确认事项、文件链接、Commit ID、验证情况、待确认项。
6. 若含多个提交，以**最终主分支状态**为准，勿将「已提交文档」等同于「线上部署已验证」。

## 对话恢复

新对话从 [START_HERE.md](./START_HERE.md) 重走入口；读取 [PROJECT_STATUS.md](./PROJECT_STATUS.md) 后核对仓库实际状态。中断事项的下一步应是可执行动作，而不是模糊的「继续」。

**下一步导航：** 处理需求 → [REQUIREMENTS.md](./REQUIREMENTS.md)；记录候选 → [IDEAS_INBOX.md](./IDEAS_INBOX.md)；技术决定 → [DECISIONS.md](./DECISIONS.md)；收尾 / 交接 → [PROJECT_STATUS.md](./PROJECT_STATUS.md)。
